# 07. Continuous Integration: Build and Push on Every Push

> **Status:** ✅ Verified on 2026-10-23 on real GitHub Actions: both build jobs passed (17 to 46 seconds each: the first run, with no build cache, took 42 and 46 seconds), the images appeared in GHCR with `latest` and full-commit-SHA tags, and a real server pulled them. The workflow also passes `actionlint`.

## Goal

Replace chapter 05's manual `docker buildx build --push` with a workflow that builds and pushes both images whenever you push to `main`. The deployment step of the same workflow comes in [chapter 08](08-auto-deploy.md).

## The workflow

`.github/workflows/deploy.yml`

```yaml
name: Build, push and deploy

on:
  push:
    branches: [main]
    paths:
      - "backend/**"
      - "frontend/**"
      - "deploy/**"
      - "scripts/**"
      - ".github/workflows/deploy.yml"
  workflow_dispatch: {}

# Run one deployment at a time and never cancel one halfway through.
concurrency:
  group: deploy
  cancel-in-progress: false

jobs:
  # ------------------------------------------------------------------
  # 1. Build both images and push them to GHCR
  # ------------------------------------------------------------------
  build:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        service: [backend, frontend]
    permissions:
      contents: read
      packages: write # lets GITHUB_TOKEN push to ghcr.io
    steps:
      - uses: actions/checkout@v7

      - uses: docker/setup-buildx-action@v4

      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      # GHCR requires lowercase image names.
      - name: Compute image name
        id: image
        run: echo "name=ghcr.io/${GITHUB_REPOSITORY,,}/${{ matrix.service }}" >> "$GITHUB_OUTPUT"

      - uses: docker/build-push-action@v7
        with:
          context: ./${{ matrix.service }}
          push: true
          platforms: linux/amd64
          tags: |
            ${{ steps.image.outputs.name }}:latest
            ${{ steps.image.outputs.name }}:${{ github.sha }}
          build-args: APP_VERSION=${{ github.sha }}
          cache-from: type=gha,scope=${{ matrix.service }}
          cache-to: type=gha,scope=${{ matrix.service }},mode=max

  # ------------------------------------------------------------------
  # 2. Tell the server to pull the new images (skipped until configured)
  # ------------------------------------------------------------------
  deploy:
    needs: build
    # Until you set the DEPLOY_HOST variable, the pipeline stops after the
    # build, so you can add the server later.
    if: vars.DEPLOY_HOST != ''
    runs-on: ubuntu-latest
    permissions:
      contents: read
    env:
      DEPLOY_TARGET: ${{ vars.DEPLOY_USER }}@${{ vars.DEPLOY_HOST }}
    steps:
      - uses: actions/checkout@v7

      - name: Configure SSH
        env:
          SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
          SSH_KNOWN_HOSTS: ${{ secrets.SSH_KNOWN_HOSTS }}
        run: |
          install -m 700 -d ~/.ssh
          printf '%s\n' "$SSH_PRIVATE_KEY" > ~/.ssh/deploy_key
          chmod 600 ~/.ssh/deploy_key
          printf '%s\n' "$SSH_KNOWN_HOSTS" > ~/.ssh/known_hosts

      # The server's authorized_keys entry for this key forces it to run
      # deploy/deploy.sh, whatever is typed here. The word after the host is
      # only a label for readers. See docs/08-auto-deploy.md.
      - name: Deploy on the server
        run: ssh -i ~/.ssh/deploy_key -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes "$DEPLOY_TARGET" deploy

      - name: Smoke test the live site
        run: ./scripts/smoke.sh "${{ vars.SITE_URL }}" "${{ github.sha }}"
```

This chapter covers the `build` job. The `deploy` job is chapter 08.

## Reading it, part by part

### When does it run?

```yaml
on:
  push:
    branches: [main]
    paths: [ "backend/**", "frontend/**", "deploy/**", "scripts/**", ".github/workflows/deploy.yml" ]
  workflow_dispatch: {}
```

- It runs on pushes to `main`, but only if something relevant changed. Editing a doc does not trigger a deployment.
- `workflow_dispatch` adds a **Run workflow** button in the Actions tab. Use it to redeploy without changing code.

### One at a time

```yaml
concurrency:
  group: deploy
  cancel-in-progress: false
```

If you push twice quickly, the second run waits for the first. It does **not** cancel it, because cancelling a deployment halfway through can leave the server in a state nobody chose.

### Two jobs from one definition: the matrix

```yaml
strategy:
  matrix:
    service: [backend, frontend]
```

GitHub runs the `build` job twice in parallel, once with `matrix.service` set to `backend` and once to `frontend`. `fail-fast: false` lets one finish even if the other fails, so a broken frontend does not hide a backend result.

### Permissions: the least that works

```yaml
permissions:
  contents: read
  packages: write
```

Every workflow run gets a temporary token, `GITHUB_TOKEN`. By default you should give it as little power as you can. This job may read the repository and write packages. That is all it can do, so a mistake or a compromised action cannot, say, push code or delete the repo.

### Logging in without a secret you manage

```yaml
- uses: docker/login-action@v4
  with:
    registry: ghcr.io
    username: ${{ github.actor }}
    password: ${{ secrets.GITHUB_TOKEN }}
```

There is no personal access token in the workflow. `GITHUB_TOKEN` is created for each run and expires when it ends. Nothing for you to rotate or leak. (This works because the images are linked to this repository. See chapter 05, step 6.)

### The image name

```yaml
run: echo "name=ghcr.io/${GITHUB_REPOSITORY,,}/${{ matrix.service }}" >> "$GITHUB_OUTPUT"
```

`GITHUB_REPOSITORY` is `owner/repo`. The `,,` is a Bash feature that lowercases the value, since GHCR refuses uppercase. The step stores the result as an output so the next step can use it.

### Build and push

```yaml
- uses: docker/build-push-action@v7
  with:
    context: ./${{ matrix.service }}
    push: true
    platforms: linux/amd64
    tags: |
      ghcr.io/.../backend:latest
      ghcr.io/.../backend:<full commit sha>
    cache-from: type=gha,scope=${{ matrix.service }}
    cache-to: type=gha,scope=${{ matrix.service }},mode=max
```

- `context` is the folder sent to Docker, `./backend` or `./frontend`. Each Dockerfile uses paths relative to its own folder.
- `platforms: linux/amd64` is the CPU of the server. On GitHub's `amd64` runners this is a native build, with none of chapter 05's cross-building trouble.
- `build-args: APP_VERSION=${{ github.sha }}` stamps the image with the commit it was built from ([chapter 08](08-auto-deploy.md) uses this to prove which version is live).
- Two tags, as in chapter 05: `latest` and the full commit SHA.
- The `gha` cache stores Docker layers between runs. `scope=` gives each service its own cache. Without it the two builds share one cache and overwrite each other's entries.

### Pinned action versions

`@v7`, `@v4` and so on are major versions. They receive fixes automatically but never breaking changes. For stricter supply-chain safety some teams pin an exact commit SHA and let Dependabot propose updates. That is a good next step. Do it when the pipeline is already working.

## Steps

1. Make sure the repository exists on GitHub and the workflow file is committed on `main`.
2. Push. Watch it: repository, **Actions** tab, **Build, push and deploy**.
3. Both `build (backend)` and `build (frontend)` should turn green. The `deploy` job shows as **skipped**. That is correct, because the `DEPLOY_HOST` variable does not exist yet (chapter 08).

## Check it worked

In the repository, **Packages** (right-hand column of the front page) should list `backend` and `frontend`. Open one: the tags are `latest` and the commit SHA of your push.

## How it works

```
  git push --> GitHub starts a fresh Ubuntu VM --> checkout code
                                                      |
                              +-----------------------+----------------------+
                              v                                              v
                  build backend image (amd64)                   build frontend image (amd64)
                              |                                              |
                              +----------------> push to ghcr.io <-----------+
```

The runner is a throwaway virtual machine. It is destroyed at the end, so nothing on it can leak into the next run. Anything you want to keep (images, caches) has to be explicitly pushed or saved.

## Common problems

| Symptom | Cause and fix |
| :--- | :--- |
| `denied: permission_denied: write_package` | The package exists but is not linked to this repository. Package settings, **Manage Actions access**, add the repo with **Write**. See chapter 05 step 6. |
| `invalid reference format` | Uppercase in the image name. The workflow lowercases it; a hand-typed tag elsewhere may not. |
| The workflow did not start | The push changed only files outside `paths:`. Use **Run workflow**, or change a relevant file. |
| `build (frontend)` fails at `npm ci` | `package-lock.json` is missing or out of date. Run `npm install` locally and commit the lockfile. |
| Works locally, fails in CI | CI builds from a clean checkout. Something you rely on may be git-ignored. Run `git status --ignored` and check. |
| The run shows an annotation that `ubuntu-latest` will move to a newer Ubuntu | Informational (seen in the real run). To avoid surprises, name a specific runner such as `ubuntu-24.04` instead of `ubuntu-latest`. |
| Does CI still work if I make the packages private? | Yes, verified: the build jobs push with the automatic token because the packages are linked to the repository, and the deploy job pulls with the server's login ([chapter 05](05-registry.md), "The private path, as verified"). |
| A second push seems stuck | It is waiting its turn (`cancel-in-progress: false`). Look at the first run. |

## Recap

- GitHub builds on a fresh `amd64` machine, so builds are reproducible and architecture-correct.
- The workflow logs in with a short-lived automatic token and has only the permissions it needs.
- Each image gets `latest` and a commit-SHA tag.
- Runs are serialised, never cancelled halfway.
